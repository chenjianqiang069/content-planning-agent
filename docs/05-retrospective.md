## 二、最难的问题

### 最难的一个：测试全绿，但验收点其实没被覆盖

这是整个项目里唯一让我意识到"差点交了个假验收"的问题。

**现象**：`over_budget` 场景（预算 10，初始方案估算 12）跑真实模型，返回 `completed`，离线测试也全绿。看起来很完美。

**但读 Trace 才发现**：模型一次都没撞超预算。它直接选了一个可行组合保存了事。题目要的核心路径 ——「估算初始方案 12 → 观察超预算 → 改选替代 → 再估算 → 保存」—— **从未发生**。

**根因**：我把素材目录（每条素材的 `cost`、`lead_days`、`quality`）直接写进了系统提示。模型看一眼提示就能心算出哪个组合可行，于是：
1. `search_materials` 形同虚设（它有时干脆不调，或只调一次做样子）
2. `estimate_cost` 的"权威成本结论"没人当真
3. 超预算这个关键观察点被模型用"预知"绕过去了

**为什么测试没抓到**：因为离线测试用的是 `MockLLM`，它按硬编码策略一定会先试 premium、撞超预算、再降级 —— 测试测的是**我的策略**，不是**模型的策略**。真实模型走了另一条更聪明的路，测试根本看不到。

**修正**：
1. 把素材目录从系统提示**彻底移除**，只保留工具费用与耗时表（规则层信息），并明确写入："素材目录不在本提示中……不要凭猜测假设素材的成本或交期；任何成本结论都要以 `estimate_cost` 的返回为准。"
2. 在场景 `notes` 里指定运营倾向的**初始方案**（`m_short_video_pro` + `m_kol_top`），复现题目参考实例的形状。

**修正后的真实 Trace**：模型老老实实先检索 → 估算初始方案 → 拿到"12.0 / 预算 10 → 不可行，缺口 2.0" → 决策依据写"初始方案超预算 2.0，降级为……" → 估算替代组合 → 可行 → 生成脚本 → 保存。题目要的路径这才真正发生了。

**教训**：
- **"测试通过"≠"验收点被覆盖"**。当被测对象是一个有自主性的模型时，用确定性 mock 写的测试只能证明"如果模型这样做，系统会正确响应"，不能证明"模型会这样做"。后者只有真实运行 + 人读 Trace 才能验证。
- **提示词里的信息量会直接改变模型的行为路径**。给太多上下文，模型会跳过工具；这正是"工具"存在的意义被削弱。设计 Agent 时要刻意保留"模型必须通过工具才能获知的信息"，否则工具就是装饰。
- 我把这条教训固化成了断言：`test_scenarios.py::test_two_execution_paths_differ` 要求 `over_budget` 必须出现 ≥2 次估算且至少一次 `feasible is False`，`normal` 必须只估算 1 次且从不出现不可行 —— 如果哪天提示词又泄露了素材目录导致模型抄近路，离线测试就会红。

### 第二难：幂等断言把"模型两次选同一方案"当成了前提

`test_real_model_repeat_run_is_idempotent` 最初断言 `plan_store_size == 1`。真实模型一跑就失败：`assert 2 == 1`。

排查后发现：预算宽裕（20）时，模型在两次运行里选了**不同**的素材组合，产生两个不同的 `plan_id`。库里 2 条记录 —— 这完全正确，两个不同方案本就该各存一条。

错的是我的断言：它把"幂等"误解成"模型两次必须选同一个方案"。幂等的真正含义是"**同一个 plan_id 绝不会被写入两次、复用既有方案的保存不重复计费**"，跟模型选不选同一个方案无关。

修正后 `runner.py` 分开报告 `same_plan_chosen` / `no_duplicate_writes` / `duplicate_saves_uncharged`，测试按两种情况分别断言。有意思的是，后来重跑时模型两次又选了同一方案（库 1 条、第二次 `duplicate=True`）—— 说明两种分支都真实存在，断言必须两边都覆盖。

**教训**：给有自主性的系统写断言时，要断言**不变量**（无论模型怎么选都必须成立的性质），而不是断言**某次具体行为**（这次选了 A，下次可能选 B）。

### 第三难：一个只有真实模型才能触发的幂等 bug

`plan_id` 是方案的唯一标识，幂等靠它。我最初的写法是：

```python
plan_id = self.plan_id(material_ids, script["script_id"])
# script_id = f"script_{self._script_seq:02d}_{sig}"   ← 问题在这
```

`_script_seq` 是**本次运行内的脚本序号**。于是同一个主题、同一组素材，如果模型在某次运行里先生成了别的脚本（探索一下别的组合），目标脚本的序号就从 `01` 变成 `02`，`script_id` 变了，`plan_id` 跟着变 —— 第二次运行不会幂等命中，方案库里出现两条本该是同一条的记录。

**为什么离线测试完全查不出来**：`MockLLM` 和 `ScriptedLLM` 每次都用固定的动作序列，脚本序号永远从 `01` 开始，两次运行的 `script_id` 必然一致，幂等断言一直绿。这个 bug 需要一个**在不同运行里探索不同路径**的模型才能撞出来 —— 只有真实模型有这种差异性。

它是被真实模型套件的失败暴露的（`assert 2 == 1`），但当时我误判成了断言写错（见上面第二条），修正断言后它"通过"了 —— 因为那次真实模型恰好两次选了同一组合、且序号都是 `01`。**直到第三次重跑才再次暴露**，这次我写了个独立脚本直接复现：让一次运行先生成别的脚本，`plan_id` 果然不同。

**修正**：脚本记录里改存**内容指纹** `sha1(style)`，它只由脚本风格决定，与执行顺序无关；`script_id` 保留（对人可读、便于追溯）但不再进入方案身份。补了两个断言：`test_plan_id_is_stable_across_runs_regardless_of_script_order`（回归）与 `test_different_script_style_yields_different_plan_id`（确认身份仍然区分内容，没把指纹改成常量）。

**教训**：
- **任何进入"身份"的值都必须与执行路径无关**。序号、时间戳、UUID、迭代顺序 —— 这些一旦掺进 hash，就会让"同一个东西"在不同运行里变成"不同的东西"，而幂等/去重/缓存全部依赖它。
- **确定性测试对"跨运行不变量"的证明力有天花板**。离线测试固定了动作序列，也就固定了序号；它验证的是"给定这条路径，幂等成立"，验证不了"任意路径下幂等成立"。这类不变量必须有非确定性的真实运行去撞。
- **测试变绿不等于修好了**。我改断言让它通过后，bug 还在，只是那次运行没触发。如果一个"修好"依赖于某次运行的偶然性，就要怀疑自己是在修代码还是在修症状。

### 第四难：终止状态判定一开始靠匹配错误文本

初版 `_finalize()` 用 `"预算超限" in step.error` 这类字符串匹配来分类终止状态。后果是：模型如果**没调 `save_plan`** 就在估算阶段判定不可行并放弃（真实模型在 `infeasible_all` 场景正是这么做的，它认为"再调 save 也没用"），就没有 `save_plan` 的失败步骤可匹配，于是被误分类成 `incomplete_not_saved` 而非 `incomplete_no_feasible_plan`。

修正：给 `StepRecord` 加结构化 `detail` 字段（`feasible` / `rejected_by` / `over_budget_gap` / `plan_lead_days` / `available_days`），状态判定完全基于结构化证据。顺带修了一个相关 bug：超期判定用 `"超出" in violation` 会把"**缺少**截止时间"误判为超期，改成比较 `plan_lead_days > available_days`。

**教训**：状态机不该建立在人类可读文案上。文案是给人看的，会改；结构化字段是给代码用的，有契约。

## 三、学习收获

### 关于 Agent 设计

1. **"决策在模型，约束在代码"是个好的分界线**。模型决定做什么（选哪个工具、哪组素材、要不要重试），代码决定什么不许做（超预算不许保存、无脚本依赖不许保存、失败不计费、上限不许突破）。这条线画清楚后，两边都简单：代码里没有业务策略分支，模型也没有能力绕过守卫。

2. **工具返回要给模型"可行动的信息"，不只是"事实"**。`estimate_cost` 不只返回 `feasible: false`，还返回 `over_budget_gap`（差多少）和 `hint`（"请改用成本更低/交付更快的素材组合"）。真实模型在 `infeasible_all` 场景里甚至利用了 `search_materials` 的降级标记（`degraded: true`）反推出"不存在更便宜的素材"。工具返回的信息密度直接决定模型重规划的质量。

3. **让模型解释自己，但别要它的内心独白**。要求模型在调用工具前用一行 `[决策依据]` 说明理由，既满足了考核"记录简要决策依据"的要求，又不需要提交内部思维过程。这些一句话理由在 Trace 里质量很高 —— 比如 `tool_failure` 场景模型写"属于可重试的瞬时错误，重试同一组素材"，`infeasible_all` 场景写"调用 generate_script 只会造成无效支出且无法保存"，都是真实的风险判断。

4. **手写循环 vs SDK `tool_runner` 的取舍要看控制需求**。`tool_runner` 更省事，但本项目需要在"调用工具 → 回传结果"这条链路上插入失败注入、步数计数、逐步 Trace、上限触发。SDK 文档自己就说"需要 SDK 未暴露的控制时退回手写循环"。60 行的手写循环换来了全部控制权，值得。

### 关于验证

5. **真实系统的验证必须真的跑真实系统**。本项目最大的坑（第二节第一条）离线测试完全查不出来。MockLLM 有它的价值（快速、免费、确定性地验证循环逻辑），但它验证的是"流程"，不是"决策"。考核文件里那句"Mock 只验证流程，不证明真实模型决策效果"是准确的，我把它写进了三处文档提醒自己。

6. **断言不变量，不断言具体行为**（见第二节第二条）。这条对有随机性的系统普遍适用。
7. **确定性测试对"跨运行不变量"有证明力天花板**（见第二节第三条）。幂等、去重、缓存这类性质依赖"同一个东西在任何运行里都得到同一个身份"，而确定性测试固定了执行路径，也就固定了序号/顺序，撞不出路径差异引发的问题。

8. **文档里的数字要从实际产出自动生成**。`examples/README.md` 的对比表最初是我手写的（写了"成本 8"），结果真实运行产出的是 9.0，文档与证据打架。改成由生成脚本从 JSON 读数字填充后，重跑也不会漂移。

### 关于工程

9. **单一口径原则**：预算计算只在 `ToolContext.breakdown()` 一处，估算和保存守卫共用。这直接消除了"估算说可行、保存说不行"这类最难查的不一致。
10. **场景定义单一来源**：`scenarios.py` 的 `Scenario` 对象被 CLI、测试、examples 生成脚本共用，改一处三处同步，避免了"文档写的用例"和"测试跑的用例"漂移。
11. **数据外置便于评审**：阈值写在 `data/rules.json` 而不是代码里，评审打开文件就能看到 `formula`、`feasible_when`、`save_guards`，不用读代码反推口径。

## 四、下一步（如果继续投入）

按投入产出比排序：

1. **启用 prompt caching**（低成本、立刻见效）。系统提示 + 工具费用表是稳定前缀，当前每场景重发 6K-19K input token 完全没缓存。加 `cache_control={"type": "ephemeral"}` 可省约 90% 的重复 input 成本，对多轮 agentic 循环收益尤其大。这是当前最明显的浪费。

2. **失败步骤续跑做成显式能力**（加分项的完整版）。现在方案库 `saved_plans` 已支持跨运行持久化，`repeat_same` 演示了在既有结果上继续。但"从上次失败的步骤精确续跑"还需要：把 `RunResult.steps` 序列化存档，重启时载入并跳过已成功的步骤（校验素材签名一致），从第一个失败/未执行的步骤继续。`ToolContext.scripts` 和 `spent` 也要一并恢复。

3. **多约束权衡的显式建模**。现在模型靠自然语言理解决策"质量 vs 成本 vs 交期"。可以给 `estimate_cost` 增加一个多目标评分（如 `utility = quality加权 - 成本惩罚 - 交期惩罚`），让模型的降级决策有更量化的依据，也便于评估"模型选的方案是否真的最优"。

4. **真实业务系统对接**。四个工具现在是本地 Mock。接真实素材库/供应商 API 时，`ToolContext` 已经与业务解耦，只需替换工具实现，守卫逻辑可复用。需要补：真实 API 的超时/重试/部分失败语义，以及计费口径与真实对账。

5. **评估集（eval）**。现在是"9 个场景 + 断言不变量"。更完整的做法是建一个覆盖更多预算/截止/主题组合的 eval 集，用真实模型批量跑，统计完成率、平均步数、重规划成功率、成本利用率，做版本间回归对比。这能把"模型决策效果"从个案观察变成可度量的指标。

6. **可观测性**。接入 OpenTelemetry，把每步的工具调用、耗时、token 用量、状态导出为 span，便于线上排查模型为什么在某类输入上反复重规划。

## 五、对考核本身的反馈（可选）

题目设计得很好，几点观察：

- **"仅有固定条件分支、自动重试或预设决策日志，不视为完成 ReAct 决策要求"** 这条很关键。它把"看起来像 Agent 的 if-else 状态机"和"真的有模型决策"区分开了。我的项目能通过这条，靠的正是第二节那个坑 —— 如果没发现提示词泄露导致模型抄近路，交上去的就是一个"预设决策日志"式的假 Agent。
- **参考实例给了具体数字（预算 10、初始 12、替代 8）**，非常好。它让"预算超限重规划"这个抽象要求变成了可精确断言的东西（我的 `test_breakdown_budget_math_matches_reference_instance` 直接断言 12 和缺口 2）。
- **"审核要点"直接点出高分依据是"合理重规划"**，这引导我把重心放在"模型能否根据工具结果自主调整"而不是"功能是否齐全"上。`infeasible_all` 场景里模型主动不调 `generate_script` 以避免无效支出，就是冲着这个要点做出的行为。
- 一个建议：可以明确说明"真实模型运行记录是否需要固定随机种子/temperature"。当前模型选择不完全确定（同一场景两次运行可能选不同可行组合），我通过"断言不变量 + 文档数字自动生成"来处理，但评审若期望可复现的固定 Trace，需要额外约定。
