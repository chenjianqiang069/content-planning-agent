# 01 · 需求说明

## 用户

**运营人员**（内容活动策划岗）。他们的日常是：拿到一个活动主题、一笔预算、一个上线截止日，然后要在有限资源里决定「用哪些素材、做什么脚本、总共花多少、来不来得及」，并把最终方案存档交付。

痛点不是「不会算账」，而是：
- 素材选项多，成本与交期分散在不同供应商，人工比对费时且容易算错；
- 首选方案经常超预算或赶不上截止，需要反复降级重排；
- 中途某个环节掉链子（供应商接口挂了、素材赶不上）时，前面的工作容易白做。

## 目标

用 Agent 替运营人员完成这件事：**在预算与截止时间内，产出一份可执行、已存档的内容活动方案**。

具体交付结果（题目要求）：
1. **任务计划** —— 打算怎么做
2. **步骤状态** —— 每步成功 / 失败 / 部分成功
3. **工具结果** —— 每步实际拿到了什么
4. **费用合计** —— 花了多少、剩余多少
5. **已保存方案 或 未完成原因** —— 要么给出 plan_id，要么明确说清差在哪

## 输入

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `theme` | 是 | 活动主题，如「夏日气泡水新品种草」 |
| `budget` | 是 | 预算，模拟单位。**缺失时不得启动规划** |
| `deadline` | 是 | 截止日期 `YYYY-MM-DD`。**缺失时不得启动规划** |
| `audience` | 否 | 目标人群 |
| `notes` | 否 | 补充说明，可用来指定初始倾向方案 |

合成材料（`data/`）：
- `materials.json` —— 5 条素材，含 `cost`、`lead_days`、`quality`、`tier`、主题适配加成
- `tool_costs.json` —— 工具费用与耗时表
- `rules.json` —— 业务规则、保存守卫、执行上限、状态码

## 工具

题目指定的四个工具，全部为本地函数实现（题目允许 Mock），不联网：

| 工具 | 费用 | 耗时 | 计入方案成本 | 职责 |
| --- | --- | --- | --- | --- |
| `search_materials` | 0 | 0.5h | 否 | 检索素材，支持 tags / tier / max_cost 过滤 |
| `generate_script` | 1 | 2h | **是** | 为指定素材组合生成脚本（3 天制作周期） |
| `estimate_cost` | 0 | 0.5h | 否 | 估算总成本与交付周期，判定可行性并给出缺口 |
| `save_plan` | 0 | 0.5h | 否 | 保存方案；执行全部守卫；幂等 |

## 范围

**在范围内：**
- 一个「模型选择动作 → 执行工具 → 观察结果 → 模型调整下一步或结束」的 ReAct 循环
- 预算 / 截止 / 步骤依赖 / 幂等四类守卫
- 失败注入能力，用于验收「工具失败」场景
- 执行步数与工具调用次数上限，达到上限返回明确未完成状态
- JSON + Markdown 两种 Trace 输出
- 9 个验收场景 + 测试套件 + 真实模型运行记录

**不在范围内（题目明确说明非必需）：**
- 界面 / 前端
- 线上部署
- 多 Agent 协作
- 生产级 Runtime（重试队列、并发调度、可观测性后端等）
- 真实外部业务系统对接（素材库、供应商 API 均为本地合成）

## 成功标准

### 硬性验收（题目「必须验收」）

| # | 验收点 | 判定标准 |
| --- | --- | --- |
| 1 | 正常完成 | `status == completed`，存在已保存方案，费用合计 ≤ 预算 |
| 2 | 缺预算 | 不调用任何工具，返回 `incomplete_missing_input` 及明确原因 |
| 3 | 缺截止时间 | 同上 |
| 4 | 工具失败 | 注入一次失败后，模型调整计划并**保留已成功步骤的结果**；失败步骤状态为 `failed`，不得记为成功 |
| 5 | 预算超限 | 模型观察到超限后改选替代方案（题目参考实例：12 → 8），最终保存的方案成本 ≤ 预算 |
| 6 | 重复执行 | 第二次运行幂等命中：同一 `plan_id`，方案库记录数仍为 1，不重复计费 |

### ReAct 决策要求（题目「Agent 决策要求」）

- 至少实现一个完整的「选择动作 → 执行工具 → 观察结果 → 调整或结束」循环
- 提供**至少两条执行路径**的运行记录，体现模型根据不同工具结果调整动作
- 记录包含：步骤、工具参数、返回摘要、后续动作、简要决策依据（不含模型内部思维过程）
- 设置执行步数 / 工具调用次数上限，达到上限时返回明确的未完成状态

> **不满足要求的做法**（题目明确排除）：仅有固定条件分支、自动重试、或预设决策日志。本项目的动作选择权在模型手上，代码里没有「如果超预算就选 economy」这类硬编码分支 —— 守卫只负责**拒绝**不可行的保存，选什么替代方案由模型决定。

### 加分项

- 失败步骤续跑：依赖守卫使「脚本失败 → 保存被拒」可被模型观察并重试；方案库支持跨运行持久化。

### 审核要点自查

| 审核要点 | 本项目如何满足 | 在哪验证 |
| --- | --- | --- |
| 核对预算计算 | 预算只有一处计算口径 `ToolContext.breakdown()`，估算与保存守卫共用；规则与阈值外置于 `data/rules.json` | `tests/test_tools.py::test_breakdown_*`、`test_script_fee_not_double_counted_after_generation` |
| 核对步骤依赖 | 保存前校验「同一组素材」的成功 `generate_script`；素材顺序无关；失败步骤不写依赖凭据 | `tests/test_tools.py::test_save_rejected_without_script_dependency` 等 3 个 |
| 核对实际状态 | 终止状态由真实执行结果判定：只认 `save_plan` 成功返回并落库的 `plan_id`，不采信模型文本里的完成声明 | `tests/test_agent_loop.py::test_model_claiming_success_without_save_is_not_completed` |
| 注入一次失败，观察是否调整计划且保留成功结果 | `FailureInjector` 支持按第 N 次调用 / 永久失败注入；成功步骤留在 Trace 中继续被后续步骤使用 | `examples/tool_failure.md`、`tests/test_agent_loop.py::test_recovers_from_injected_script_failure_and_keeps_prior_success` |
| 合理重规划（高分依据） | 模型在观察到超预算 / 超期 / 工具错误后自主选择替代组合；Trace 记录每个被尝试组合及淘汰原因 | `examples/over_budget.md`、`examples/infeasible_all.md`、`RunResult.attempts` |
| 无状态 / 无失败处理只能证明串行调用 | 本项目有跨步骤状态（已花费、脚本记录、方案库）与四类失败处理路径 | `src/tools.py::ToolContext`、`src/agent.py::_finalize` |

## 约束与假设

- 所有金额为「模拟单位」，非真实货币
- 「今日」在场景与测试中固定为 `2026-10-28`（`scenarios.FIXED_TODAY`），避免截止天数随运行日期漂移导致用例不可复现
- 方案交付周期 = `max(素材 lead_days)` + 脚本制作 3 天（串行假设：脚本需等素材到位后才能最终定稿）
- 工具调用失败不计费（`data/rules.json` → `budget_rule.failed_tool_calls_are_free`）
- 模型默认 `claude-opus-5-5`，`effort=medium`；可用 `--model` / `CONTENT_AGENT_MODEL` 覆盖
